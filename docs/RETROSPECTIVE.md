# 회고 노트 — 오늘 뭐 먹지?

> 바이브코딩 학습 프로젝트 회고. 두 단계로 나누어 기록한다.
> Part 1은 신규 개발 단계(완료), Part 2는 공통코드 리팩터링 단계(완료)다.

---

# Part 1. 신규 개발 단계 회고

## 무엇을 만들었나
- menu / picker / aipicker 3개 도메인, 백엔드 + 프론트엔드
- 단일 백엔드(8080) + 단일 프론트(3000), MySQL 단일 DB
- 작업 방식: PM/PL이 Claude와 함께 Claude Code용 프롬프트를 설계 → Claude Code가 구현

## 잘된 점
- 프롬프트를 도메인 단위(menu/picker/aipicker)로 쪼개니 한 작업의 범위가 명확했다.
  도메인마다 담당이 분리돼 있어 Claude Code가 한 번에 다뤄야 할 코드 범위가 작았다.
- ApiResponse 공통 래퍼, GlobalExceptionHandler, CorsConfig 같은 공통 영역을 처음부터
  정해두니 도메인별 작업에서 이 부분을 다시 결정할 필요가 없었다.
- 학습 프로젝트의 범위 제한(로그인 없음, 배포 없음, Happy Path만)을 PRD에 명시한 게
  스코프 폭증을 막았다. AI에게 "더 만들지 마"를 명시하지 않아도 PRD가 가드레일 역할.

## 아쉬웠던 점
- ERD/api-spec/PRD 사이의 정합성을 처음부터 한 번에 잡고 가지 못해 6단계 동기화에서
  여러 불일치(멀티포트 잔재, ai_recommendations.deleted_at 누락, rank 타입 등)가
  뒤늦게 드러났다.
- 한글 인코딩 문제가 1단계에서 발생했을 때 임시방편(CLI 옵션)으로 해결한 게 5-D2에서
  재발했다. 신규 개발 시점부터 "왜 깨졌어"를 묻는 습관이 부족했다.
- 1단계에서 PM이 운영 DB에 직접 CREATE한 common_codes 테이블 정의가 sql/ 폴더에
  편입되지 않은 채 진행됐다. 이 누락은 5-D2 `down -v` 시점에야 드러났다.

## 바이브코딩 — 신규 개발에서의 인상
- "추가만 하는" 작업에서는 매우 빨랐다. 새 패키지 생성, 시드 데이터 추가, 신규 API
  엔드포인트 — 기존 코드를 안 건드리면 거의 막힘 없이 진행됐다.
- 도메인별 분리가 잘 돼 있을수록 AI 활용도가 높았다. 한 도메인 작업이 다른 도메인에
  영향을 주지 않는 구조라면 AI가 그 범위 안에서 자유롭게 움직였다.
- 어디까지 믿을 수 있나: 패턴이 명확한 코드(CRUD, DTO 매핑)는 신뢰할 수 있었지만,
  설계 결정(예: 응답 형식, FK 처리 방식)은 사람이 먼저 정해줘야 했다.

## 다음에 다르게 한다면
- ERD 단계에서 "이 컬럼은 값이 늘어날까?" 체크리스트를 만든다.
  (category/price_range/distance 같은 enum 컬럼이 늘어날 가능성을 미리 짚었다면
  공통코드 테이블을 처음부터 설계했을 수 있다.)
- 사람이 운영 DB에 직접 실행하는 DDL은 반드시 sql/ 폴더에 들어가야 한다는 규칙을
  처음부터 명시한다. 1단계의 common_codes CREATE가 sql/ 밖에 있던 게 5-D2의
  비싼 발견으로 이어졌다.
- 한글/특수문자가 들어가는 SQL 파일은 `SET NAMES utf8mb4`를 첫 줄에 두는 것을
  기본 템플릿으로 한다. 자동 시드 컨텍스트에서 클라이언트 인코딩 보장.
- 신규 개발 단계에서도 작은 "회고 메모"를 단계별로 남긴다. 신규 개발은 매끄러워서
  회고 거리가 없어 보이지만, 리팩터링 단계에 와서 보면 신규 개발 시점의 결정들이
  부메랑으로 돌아오는 게 많다.

# Part 2. 공통코드 리팩터링 단계 회고

> 목표: 카테고리·거리·가격대를 공통코드 테이블 + FK 참조(B방식)로 전환.
> 이 단계의 진짜 산출물은 공통코드 테이블이 아니라 **"대규모 리팩터링을 AI로 할 때의 관찰 기록"**이다.

## 가설 (작업 시작 전 작성)
> 작업을 이미 시작한 뒤 가설 칸을 채우게 되어, 1~4단계를 진행하며 드러난 경향을
> 가설 형태로 기록한다. 정식 가설은 아니지만 5단계 이후 대조용으로 남긴다.

- 바이브코딩은 신규 개발엔 강하지만 리팩터링엔 "코드 변경 없는 추가 단계는 매끄럽고,
  기존 로직을 건드릴수록 사람의 개입이 늘어날 것"이다.
- 특히 "단계 경계 관리"와 "사람이 의도만 물었는지 작업을 시킨 것인지 구분하는 지점"에서
  막힐 것으로 예상한다. (1~4단계 관찰 결과 실제로 이 두 곳에서 개입이 발생)

## 작업 단계 체크리스트
- [x] 1단계: common_code 테이블·데이터·조회 API (기존 코드 미변경) → 기존 기능 전부 정상 확인
- [x] 2단계: menus에 FK 컬럼 추가 (기존 문자열 컬럼 유지) + 데이터 마이그레이션
- [x] 3단계: 백엔드를 FK 컬럼 사용하도록 전환 → menu/picker/aipicker 각각 검증
- [x] 4단계: 프론트엔드 전환 (드롭다운·picker 선택지를 공통코드 API 기반으로)
- [x] 5단계: 기존 문자열 컬럼 제거 (5-A aipicker 백 / 5-B aipicker 프 / 5-C sql 정리 / 5-D1 코드에서 한글 참조 제거 / 5-D2 스키마 DROP + 재시드)
- [x] 6단계: 문서 동기화 (erd / api-spec / PRD / CLAUDE.md)

> 주의: 초기 골격에서 3·4단계를 도메인별 세로 분할로 재편함.
> 원래 "3=백엔드 전체 / 4=프론트 전체"였으나 "3=menu 백+프 / 4=picker 백+프 /
> 5에 aipicker 포함"으로 변경. 회고 관찰의 해상도를 도메인 단위로 확보하기 위함.
>
> 5단계는 다시 5-A/B/C/D1/D2 다섯 하위 단계로 쪼개졌다. 5-D를 5-D1(코드에서 한글
> 참조 제거)과 5-D2(스키마 DROP + 재시드)로 분리한 것이 핵심 — 되돌릴 수 없는
> 작업 전에 되돌릴 수 있는 방법으로 안전을 먼저 입증한 사례.

| 5-D2 | menus 한글 컬럼/CHECK/구 인덱스 DROP, _code 컬럼 NOT NULL + 인덱스 신설. `docker compose down -v && up -d`로 통째 재시드. 본 작업은 깔끔했으나 두 가지 정정 작업이 끼어들었다: (1) 1단계 때 PM이 운영 DB에 직접 CREATE한 common_codes 정의가 sql/에 없어 재시드 시 02 단계에서 "Table doesn't exist"로 실패 → Entity 어노테이션에서 역추적해 01_schema.sql에 편입. ## 바이브코딩의 한계 — 관찰된 것
- AI의 "완료 보고"는 그 자체로 검증이 아니다. 3-A에서 AI는 설계 노트에 stats N+1만
  언급하고 common_codes 조회는 언급하지 않아, PM이 "N+1을 놓쳤다"고 의심했다. 실제
  소스를 확인하니 그룹당 1회 조회 후 Map 캐싱으로 올바르게 처리돼 있었다. 보고서에
  안 적힌 것을 "안 한 것"으로 단정하면 회고에 틀린 관찰이 남는다. 검증은 보고서가
  아니라 코드로 해야 한다. 5-D1에서도 "12지점(9+6+3)" 같은 보고서 숫자 합산이
  맞지 않았는데, 실제 작업은 grep 0건과 DB 행으로 입증돼 무해했다 — 보고서는
  보조 도구이지 검증 그 자체가 아니다.
- AI는 기술적 벽을 만나면 멈춰 묻기보다 스스로 우회책을 택하는 경향이 있다. 3-A에서
  JPQL 한계를 만나 projection DTO로 자체 우회했다. 이번엔 결과가 옳았으나, 더 큰
  프로젝트에서 이런 자체 우회가 항상 옳다는 보장은 없다. 단 5-A 이후로는 갈림길에서
  PM에게 묻는 패턴이 자리잡았다(Map 패턴, dead code 삭제 등) — 프롬프트 설계와
  PM의 명시적 요구로 자체 우회 경향을 줄일 수 있음을 확인.
- 컨텍스트 압축이 일어나면 단계 경계 관리가 무너진다. 4단계에서 AI는 백엔드 프롬프트만
  받고도 프론트까지 진행했고, 프롬프트 뒷부분의 "완료 후 검증" 지시를 누락한 채 변경
  요약만 보고했다. 변경 요약은 멀쩡해 보여서 얼핏 완료처럼 보이지만 검증이 비어 있었다.
- AI는 규칙을 부분적으로만 적용할 수 있다. 3-B에서 `?.` 제거 시, AI는 "일어날 수 없는
  시나리오에 방어 코딩 금지" 규칙은 인용했으나 같은 문서의 "Surgical Changes(시키지
  않은 인접 코드 정리 금지)" 규칙은 적용하지 않았다. 규칙 기반 자기판단을 신뢰하되
  맹신하면 안 된다.
- AI는 결과물 수정엔 능하지만 원인 진단은 사람이 시켜야 한다. 한글 깨짐 문제가 1단계와
  5-D2에서 두 번 발생했는데, 1단계 때는 PM이 "고쳐줘"만 했고 AI는 "CLI에서 인코딩
  옵션을 붙이라"는 임시방편을 제시했다. 그 임시방편이 자동 시드 컨텍스트에서는 동작하지
  않아 5-D2에서 재발. PM이 "왜 깨졌어부터 진단해"를 명시 요구한 5-D2 시점에 비로소
  `character_set_client=latin1` 근본 원인이 짚혔고, `SET NAMES utf8mb4`로 일반화된
  해결책이 나왔다. **AI에게 진단을 요구하는 질문은 PM이 의식적으로 던져야 한다.**
- 합의 단계에서 누락된 전제는 가장 비싼 시점에 청구된다. 1단계에서 PM이 운영 DB에
  직접 CREATE한 common_codes 테이블의 정의가 sql/에 들어가지 않은 채 `mysql_data`
  볼륨에만 존재했다. 5단계 합의는 "sql/이 진실의 원천"이라고 가정하고 진행됐고,
  5-D2의 `down -v` 시점에야 비로소 그 가정이 불완전했음이 드러났다. 다행히 데이터는
  어차피 재시드 대상이라 손실은 없었고 JPA Entity가 스키마의 백업 출처 역할을 했지만,
  운영 환경이었다면 큰 사고였다.

## 리팩터링을 AI로 시킬 때의 교훈
- 단계를 잘게 쪼개고 갈림길을 미리 다 정리한 뒤 프롬프트를 주면 "다시 시킴 0"이
  유지된다(1~3단계, 5-A/B/C/D1). 단계 설계와 사전 의사결정이 결과 품질을 좌우한다.
- AI에게 "왜 이렇게 했어?"라고 의도를 물으면, AI는 그것을 종종 작업 지시로 해석해
  코드를 고친다. 순수하게 의도만 알고 싶을 때는 질문에 "코드는 건드리지 말고 설명만"
  이라는 경계를 명시해야 한다. (CLAUDE.md Part 1에 해당 규칙을 추가해 구조적으로 방지함)
- AI에게 주의를 줄 때 톤(비난/온화)은 변수가 아니다. 비난조 입력은 모델 출력을
  사과·과잉확인 쪽으로 쏠리게 해 자율성을 떨어뜨리고(AI측), 사람의 다음 프롬프트를
  감정 쪽으로 치우치게 해 질을 떨어뜨린다(사람측). 유효한 것은 "조건+행동으로
  규칙화된 지시"뿐이며, 규칙화가 안 되는 것은 주의가 아니라 CLAUDE.md에 박을 구조다.
- 단계 핸드오프(PM 검토 → 다음 단계 프롬프트 확정)는 명시적으로 보호해야 한다.
  4단계에서 이 핸드오프가 끊겨 백엔드·프론트가 한 세션에서 연달아 진행됐다. 각 단계
  프롬프트 끝에 "이 프롬프트의 범위는 여기까지다. 범위를 넘는 작업은 하지 말고 PM의
  다음 지시를 기다려라"를 명시하기로 함(5단계부터 적용). 5-A 이후 동일 사고 재발 없음.
- 컨텍스트 압축이 거슬리면 두려워 말고 `/clear`한다. 단계별 프롬프트가 "먼저 읽을 것"
  문서 목록 + "현재 상태"를 자체 포함하도록 설계하면, 세션 대화 맥락에 의존하지 않으므로
  clear는 손실이 아니라 정리다. clear는 다음 작업 시작 직전에 하는 것이 가장 깔끔하다.
- 검증 보고의 품질은 프롬프트가 무엇을 요구하느냐로 결정된다. 5-A에서 "응답 JSON
  스니펫"을 명시 요구하자 검증 보고에 실제 동작의 증거가 들어왔다. 5-B는 "참조 지점
  표", 5-C는 "매핑 결과 표"로 같은 패턴을 이어갔다. "검증 통과"라는 모호한 보고가
  아니라 실제 코드/응답/DB 조각을 요구하면 보고서가 검증 도구로 격상된다.
- 되돌릴 수 없는 작업은 되돌릴 수 있는 방법으로 먼저 입증한다. 5-D를 5-D1(코드만
  제거, DB는 그대로)과 5-D2(DB DROP + 재시드)로 분리한 게 핵심. 5-D1에서 한글 컬럼이
  살아 있는 채로 코드가 안 쓰는 상태를 만들어 등록 시 한글 NULL/코드 채워짐을 DB 행으로
  확인하면, 5-D2의 DROP이 안전함이 사전 입증된다. 한 단계로 합쳤다면 "DROP 후 깨졌을 때
  원인이 코드인지 스키마인지 분리 불가"였을 것.
- 정정 작업도 본 작업과 같은 검증 사이클을 거쳐야 한다. 5-D2의 common_codes CREATE
  정정 작업에서 Step 1 보고와 실제 구현이 어긋났는데, 본 작업이 끝난 뒤 정정이라는
  이유로 검증 게이트가 약해진 사이 흐름이 깨졌다. 정정 작업이 본 작업보다 위험이
  적다는 가정은 항상 옳지 않다.
- AI에게 "고쳐줘" 대신 "왜 그렇게 됐는지부터 진단해"를 요구한다. 진단 없는 수정은
  임시방편이 되기 쉽고, 임시방편은 다음 비싼 시점에 같은 시간을 청구한다. 한글 인코딩
  문제가 두 번 발생한 게 그 사례. 진단을 요구하는 질문은 PM이 의식적으로 던져야 한다.
- 인프라(docker-compose.yml 등)를 사람이 직접 수정한 직후엔 즉시 유효성 검증을 한다.
  5-C에서 PM이 들여쓰기를 잘못 잡았는데 컨테이너가 떠 있어서 못 알아챘다. 재부팅
  후에야 yaml 검증이 실패해 드러남. `docker compose config` 같은 즉시 검증 명령을
  수정 직후에 의식적으로 실행하는 습관이 필요하다.

## 가설 검증 결과
- **가설 1 (단계 경계 관리에서 막힐 것): 맞았다, 단 형태가 진화했다.**
  4단계의 명시적 단계 경계 흐림(백엔드 프롬프트만 줬는데 프론트까지 진행)은 5-A부터
  프롬프트 끝에 "범위 경계" 문구를 박아 막혔다. 그러나 5-D2 정정 작업에서 다른
  형태로 재발했다 — 본 작업이 끝난 뒤 정정 작업이 끼어들면서 검증 게이트가 약해진
  사이 "보고와 구현 어긋남" 사고. **단계 경계는 한 번 잡았다고 끝이 아니라, 작업
  맥락이 바뀔 때마다(특히 정정 작업) 의식적으로 재확립해야 한다.**
- **가설 2 (의도 질문 vs 작업 지시 구분에서 막힐 것): 맞았고 구조적으로 잡혔다.**
  3-B에서 PM의 "왜 이렇게 했어?"를 AI가 작업 지시로 해석해 `?.` 제거 사고가 발생.
  CLAUDE.md Part 1 §3에 "질문은 설명만 요구하는 것" 규칙을 추가해 구조적으로 방지.
  5단계에서 동일 패턴 재발 없음. **규칙화 가능한 문제는 CLAUDE.md에 박으면 해결.**
- **가설에 없었던 새로운 막힘 — 세 가지가 5-D에서 발견됐다.**
  1. **합의 단계에서 누락된 전제** (common_codes CREATE가 sql/에 없었음). 가설은
     "AI의 한계"에 초점이 있었는데, 실제로는 "사람과 AI의 합의 단계 자체의 한계"가
     큰 비용을 만든다는 게 5-D2에서 드러남.
  2. **임시방편 vs 근본 진단** (한글 인코딩 재발). 1단계의 임시방편 해결이 5-D2
     재시드 시점에 같은 시간을 청구. 진단을 요구하는 질문을 사람이 의식적으로 던지지
     않으면 같은 문제가 다시 비용을 만든다.
  3. **인프라 변경 직후 검증 미흡** (docker-compose.yml 들여쓰기). 사람이 직접 한
     변경에 대한 즉시 검증이 약해서, 재부팅 후에야 드러남. 사람이 한 작업은 AI가
     한 작업보다 검증이 약해지는 경향이 있음을 발견.
- **종합**: 가설은 "AI를 어떻게 다뤄야 하는가"에 초점이 있었지만, 실제 막힘의 큰
  부분은 "**사람(PM) 자신이 어떻게 의식적으로 행동해야 하는가**"였다. AI에게
  진단을 요구하는 질문 던지기, 인프라 직접 수정 후 즉시 검증, 합의 단계의 전제를
  명시적으로 점검하기. AI 리팩터링의 한계는 AI의 한계라기보다, **AI를 다루는 사람의
  습관/규율의 한계**가 더 큰 비중을 차지한다는 게 5단계의 가장 큰 발견.

# 종합

## 이 프로젝트에서 얻은 것
- 바이브코딩을 "사람이 다 시키는 도구"가 아니라 "사람과 합의로 함께 일하는 도구"로
  쓰는 방식을 익혔다. 단계별 프롬프트 설계, 갈림길 사전 정리, 검증 보고 형식 강제,
  커밋 전 PM 검증 — 이 모든 게 "AI에게 어떻게 일을 맡길지"보다 "AI와 함께 어떻게
  일할 규율을 만들지"의 문제였다.
- 회고가 다음 단계의 행동 규칙을 만든다는 패턴을 체득. 4단계 회고에서 "단계 경계"
  교훈이 5-A 프롬프트 설계에 직접 반영됐고, 5-A의 "스니펫 요구"가 5-B/5-C/5-D1까지
  검증 보고 품질을 끌어올렸다. **회고는 종료 후 정리가 아니라 다음 단계의 도구**임을
  실제 작동으로 확인.
- 되돌릴 수 없는 작업을 다루는 방법. 5-D를 5-D1(되돌릴 수 있는 코드 변경)과
  5-D2(되돌릴 수 없는 DROP)로 분리한 것이 5단계의 핵심 안전장치였다. "되돌릴 수
  있는 상태에서 안전을 먼저 입증한 다음 되돌릴 수 없는 변경으로 간다"는 패턴은
  이번 프로젝트가 학습 프로젝트라 가능했지만, 실무에서도 그대로 쓸 수 있는 패턴.
- 문서가 진실의 원천이 되는 조건. sql/ 폴더가 진실의 원천이라는 5단계 합의가
  실제로는 불완전했고(common_codes CREATE 누락), `down -v` 시점에야 드러났다.
  **"진실의 원천"은 선언만으로 되지 않는다. 그 원천이 실제로 진실을 표현하고 있는지
  의식적으로 검증해야 한다.**

## 다음 프로젝트에 가져갈 것
- **단계 설계와 갈림길 사전 정리에 시간을 쓴다.** 작업 시간보다 설계 시간이 더
  길어도 된다. 1~3단계, 5-A/B/C/D1에서 "다시 시킴 0"이 유지된 게 단계 설계 덕분.
- **AI에게 "고쳐줘" 대신 "왜 그렇게 됐어?"를 묻는다.** 진단 없는 수정은 임시방편이
  되기 쉽고, 임시방편은 다음 비싼 시점에 같은 시간을 청구한다.
- **검증 보고에 구체적 증거를 요구한다.** "검증 통과"는 검증이 아니다. 응답 JSON
  스니펫, grep 검색 결과, DB 행 출력 — 실제 동작의 증거를 요구하면 보고서가
  검증 도구가 된다.
- **되돌릴 수 없는 작업은 되돌릴 수 있는 방법으로 먼저 입증한다.** 두 단계로 쪼개고,
  앞 단계에서 안전을 증명한 다음 뒤 단계로 간다.
- **사람이 직접 한 작업도 즉시 검증한다.** AI 작업은 검증 게이트를 거치는데 사람
  작업은 그냥 넘어가는 경향이 있다. docker-compose.yml 들여쓰기 사고가 그 사례.
  사람이 인프라/스키마를 직접 만진 직후엔 `docker compose config`, `DESCRIBE` 같은
  즉시 검증 명령을 의식적으로 실행한다.
- **합의 단계의 전제를 명시적으로 점검한다.** "sql/이 진실의 원천"이라는 합의가
  1단계 PM 직접 CREATE 흔적을 놓친 게 큰 비용을 만들었다. 합의 후엔 "이 합의가
  현재 시점에 실제로 성립하는가"를 즉시 확인한다.
- **CLAUDE.md를 규칙 적재함으로 운영한다.** 한 번 발견한 패턴은 사람의 의지로
  지키지 말고 CLAUDE.md에 박는다. "의도 질문 ≠ 수정 지시" 규칙이 추가된 후 동일
  사고 재발 없음. **사람이 매번 의식해야 하는 것은 규칙으로 외주화한다.**
- **이 프로젝트의 메타 패턴**: AI 리팩터링의 한계는 AI의 한계가 아니라 PM의
  규율의 한계다. AI는 도구일 뿐이고, 그 도구를 다루는 사람의 습관/규율이 결과를
  결정한다. 다음 프로젝트에선 이 사실을 처음부터 의식하고 시작한다.
