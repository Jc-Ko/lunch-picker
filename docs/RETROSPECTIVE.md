# Part 2. 공통코드 리팩터링 단계 회고

> 목표: 카테고리·거리·가격대를 공통코드 테이블 + FK 참조(B방식)로 전환.
> 이 단계의 진짜 산출물은 공통코드 테이블이 아니라 **"대규모 리팩터링을 AI로 할 때의 관찰 기록"**이다.

## 작업 단계 체크리스트
<!-- 단계별로 "전체가 여전히 도는지" 검증하며 진행 -->
- [ ] 1단계: common_code 테이블·데이터·조회 API (기존 코드 미변경) → 기존 기능 전부 정상 확인
- [ ] 2단계: menus에 FK 컬럼 추가 (기존 문자열 컬럼 유지) + 데이터 마이그레이션
- [ ] 3단계: 백엔드를 FK 컬럼 사용하도록 전환 → menu/picker/aipicker 각각 검증
- [ ] 4단계: 프론트엔드 전환 (드롭다운·picker 선택지를 공통코드 API 기반으로)
- [ ] 5단계: 기존 문자열 컬럼 제거
- [ ] 문서 동기화 (erd / api-spec / PRD / CLAUDE.md)

## 관찰 기록
<!-- 작업하면서 그때그때 채운다. 이게 이 노트의 핵심이다. -->

| 단계 | 무슨 일이 있었나 | AI가 막히거나 빠뜨린 것 | 다시 시킨 횟수 | 메모 |
|------|-----------------|----------------------|--------------|------|
| 1 | 신규 패키지·시드만 추가, 기존 코드 무수정 | 없음 | 0 | 기존 코드 미변경 단계라 난이도 낮음. 진짜 관찰은 2~5단계. 한글데이터가 깨져서 들어가서 안깨지게 수정하라고 요청 |
| 2 | menus _code 컬럼 마이그레이션 (상관 서브쿼리로 common_codes 참조) | 없음. 하드코딩 안 하고 JOIN/서브쿼리 사용 — 지시 준수 | 0 | menus id 17 결번(테스트 중 추가·삭제) — 5단계 02_sample_data 정리 시 처리 |
| 3-A | menu 백엔드 코드 전환. 응답 객체화·이중 쓰기·코드 검증 통과 | 막힘·누락 없음 | 0 | JPQL 중첩객체 한계를 projection DTO(MenuWithStatsDto)로 자체 우회. common_codes는 그룹당 1회 조회 후 Map 캐싱 — N+1 없음 |
| 3-B | 막힘·누락 없음. 단, 검증 후 PM의 "의도 확인 질문"을 수정 지시로 해석해 ?.을 자발적으로 제거 | 없음 | 0 | ① "왜 이렇게 했냐"는 질문 → AI는 작업 지시로 해석함. 의도만 물을 땐 "코드 건드리지 말고"를 명시해야 함. ② AI가 "방어코딩 금지" 규칙은 인용하면서 "Surgical Changes" 규칙은 누락 — 규칙 기반 자기판단이 부분적. ③ 대응: CLAUDE.md Part 1에 "의도 질문≠수정 지시" 규칙 추가. AI에게 주의를 줄 때 톤(비난/온화)은 변수가 아니다. 비난조 입력은 모델 출력을 사과·과잉확인 쪽으로 쏠리게 해 자율성을 떨어뜨리고(AI측), 사람의 프롬프트를 감정 쪽으로 치우치게 해 질을 떨어뜨린다(사람측). 유효한 건 "조건+행동으로 규칙화된 지시"뿐이며, 규칙화가 안 되면 그건 주의가 아니라 CLAUDE.md에 추가할 구조적 규칙이다. |
| 4 | picker 백+프 전환. simple=GET/weighted=POST 분리, 비중 동적구조, 균등 fallback 구현 | 4-A 프롬프트만 줬는데 프론트까지 자체 진행 후 "4-B 완료"로 보고 → 백엔드 변경이 보고서에서 누락돼 단계 추적 혼선. 작업 자체는 정상 | 1 (검증 누락분 재요청) | 압축 + "프론트는 4-B에서" 문구가 겹쳐 단계 경계가 흐려짐. 검증이 curl·번들 grep 기반이라 실제 브라우저 클릭 검증은 PM이 별도 수행 필요 |
